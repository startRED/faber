# g390t: recorded token attribution and safe trimming

Status: Investigation and implementation complete, with explicit attribution limits. All requested local proofs passed. The change is proposed on `trim-tokens`; it has not been merged. No model, judge, account-reader or benchmark invocation was made.

## Three causal findings, in order of the evidence available

1. **A second turn just to conclude already checked work: 449,335 tokens and 66.248 assistant seconds across four requests.** This accounts for 75.15% of the reported 597,898-token excess and 36.93% of the 179.40-second wall-time excess (assistant time and wall time are different clocks). `engine/src/engine/ended.rs:181` asks the model to check again and call `wrap_up`; `:284` selects that request and `:301` sends it. `engine/src/progress.rs:114` describes the original conclusion call as optional, although R509 requires it. The four extra turns contain only a repeated check command and `WrapUp`, no file changes. Three requests tie; the to-do quality win was already implemented before the wake. **Repeated execution is waste; the structured conclusion itself is required and useful.** Removing the conclusion guard would violate R509 and is not proposed. Make the existing call explicit before the original final answer and reuse still-current evidence instead.

2. **Repeated, larger input context, including Faber's standing prompt and tool definitions.** Cache reads rise by **553,088**; input including cache rises by **596,847**; generated output rises by only **1,051**. The conclusion turns above alone reread **444,032 cached tokens**, leaving **109,056 additional cache reads** outside those turns. After excluding those whole follow-ups, the remaining Faber usage is **1,087,568 versus 939,005**, still **148,563 higher (+15.82%)**. These are measured context-processing differences, **not a measured allocation of that residual to prompt bloat**. `engine/src/codex.rs:1196-1210` appends persona, project rules, lead instructions and optional group instructions; `:1215-1253` offers dynamic tools; `:1597-1613` adds start card, lazy skill discovery and guide index. `engine/src/persona.rs:6-15` has 1,362 characters of project details, 203 of bigger-offer instructions and 2,144 of lead instructions. Each of five project start cards is **685 characters**; Chat has none. The saved all-tools offline baseline is **6,273 estimated tokens**, plus **741 estimated persona tokens** (`scripts/tool-tokens/baseline.json`), **not the run's tokenizer measurement or necessarily its offered set**. No catalog skill body was selected in any row; saved kit IDs are empty and resource digests are the empty digest. The **11,229-character guide file is lazy, not injected whole**, and no recorded tool reads it. User-installed ponytail was read in four coding rows; it is not a Faber catalog installation. Quality wins exist for planning, to-do and research; no evidence isolates which standing instructions caused them. **Some unused definitions are candidates, but deleting capabilities or user instructions without a quality-preserving boundary is not justified.**

3. **Auxiliary calls outside the reported tokens: 8/8 first routes time out, 8 unmetered ledger entries, plus five completed title-generation calls. Token counts are unknown.** Each saved first route has `act.why.routerTimeout`, and each budget has `codex.unmetered[20763] = 1`. All answers use `gpt-6.1-sol@medium`, the plain model/effort. `engine/src/engine/auto.rs:12-14` permits 2.5 seconds; `:266-287` asks whenever there are multiple candidate model profiles, even with one vendor; `:295-330` opens/sends the router and records an unknown timeout span. This is **up to 20 seconds of configured waiting across eight first sends**, not an independently measured 20 seconds of extra wall time. Each spawn log records four app-server launches; those include bootstrap/auxiliary work and are **not four model calls**. Automatic titles add another auxiliary model path (`engine/src/engine/title.rs:68-115`), called after the first answer (`engine/src/engine.rs:3734`): five project rows have generated titles and positive non-answer ledger cost; the three Chat rows retain fallback titles, so their title-call completion is unproven. **No answer-quality win can be credited to a route verdict never received or a title-only call.** The wins came from the answer path. Globally disabling Auto or skipping classification for one vendor would lose model/effort selection when several profiles are available, so that cut is not safe on these data. Fixing router startup/latency needs separate evidence; no quota-consuming experiment was run.

Findings 2 and 3 cannot be ranked by exact attributable token cost: the capture does not contain first-request serialized prompts, per-native-step usage or router counters. The three entries above distinguish measured cost, structural cause and missing measurement rather than inventing an additive explanation.

## Task 2 decision and boundaries

Implement only an earlier, explicit conclusion contract in the shared tool description, replacing the optional wording and preventing an instruction to rerun unchanged successful checks. Both vendors already share that description. Keep all evidence requirements, blocked/needs-you outcomes, the mandatory wrap-up record and the bounded recovery wake. The pure prompt-contract regression failed on the old description, then passed on the new one without any model call. This is a prevention improvement with a measured historical opportunity of 449,335 tokens, **not a claim that the same saving has been experimentally achieved**.

Do not remove the R509 guard, tools, guide availability, user skills, independent review, validation or research. Those changes would alter quality or product guarantees. Do not disable one-vendor Auto: it chooses models/efforts too. Do not rerun this benchmark. The implementation uses `trim-tokens` from fetched `origin/phase-1-base` at `4894add5`; no ship/land operation is authorized.

Remaining measurement blocker: exact prompt-versus-native-iteration attribution for all eight rows and numerical auxiliary tokens cannot be reconstructed because the harness discards native events (`g390c2-evidence/final-run/harness/engine/examples/bench.rs:332-345`) and does not persist serialized first requests; the ledger has costs/unknown spans rather than auxiliary token counters (`bench/pure.rs:524-526`). No new model call is allowed to fill these gaps.

## Implemented change and verification

`trim-tokens` starts at `4894add58d7d2903fad15e6ee3ef9a407c1a9812`. No process, stored state, permission, guard or tool capability changed; no new resident allocation or CPU task was added.
