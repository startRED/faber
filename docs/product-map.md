# Product map

What Faber has today, for whoever builds the next part. [product-rules.md](product-rules.md) says where a new thing goes;
this page says what is already there, so a new part extends it instead of adding a second way to do the same thing. How
each part looks and moves is in [design/](design/README.md); where Faber is going is in [product/](product/README.md).

The map names files and keys, never line numbers. `engine/tests/product_map.rs` fails when a setting, a `ui/*.tsx` file,
a shell command or a browser storage key is missing from it; words, flows and features stay true because the commit
that changes them updates this page too. Last full audit: 2026-10-16.

### Project instruction discovery

Faber launches each project in its folder or conversation copy; Memory edits the selected project folder. Discovery follows [Claude Code's guide](https://code.claude.com/docs/en/memory) and [Codex's guide](https://developers.openai.com/codex/guides/agents-md) (`engine-drivers/src/claude.rs`, `engine-drivers/src/codex.rs`).

- Claude Code reads `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md`, along with its other instruction sources; it can fall back to `AGENTS.md` and `.claude/AGENTS.md`.
- Codex selects the first nonempty `AGENTS.override.md` or `AGENTS.md` per folder, followed by configured fallback names. Memory lists the selected file.
- Faber keeps each tool's discovery rules and does not inspect home folders or infer their settings.

## Every setting

`settings.json` in the data folder holds the struct `Settings` of `engine-core/src/model.rs`; `ui/api.ts` mirrors it by hand.
The `save_settings` command (loading old `verbosity` rewrites it once as `replyStyle`: low to short, high to explained, medium/default to default, then drops the old key; an existing new choice wins) and plan approval share `Core::save_settings` (`engine/src/engine.rs`), whose merge builds a

## Other stored state

Temporary Chat extends Conversation: `Conversation.temporary` is opt-in; the engine excludes it from summaries, search, prompt history, Auto learning and recents exports, and removes its owned files, attachments and CLI session on close, conversation switch, shutdown or the next startup after a crash. Ordinary conversations survive. The UI keeps its composer, prompt-edit, quick-question and queued-edit drafts in memory only; it saves no model choice or reading position for it. Checks: `engine/tests/engine.rs` (`temporary_chat_`), `engine-store/src/search.rs` (`temporary_conversations_do_not_enter_search_or_history`), `engine/src/engine/temporary.rs`, and `tests/ui/sidebar-exit.check.ts` (`temporary chat`).

Review rounds are saved on `Message.review`. Only identical findings combine reviewers (`review::tests::t515a_distinct_problems_in_one_file_never_become_consensus`).

Recovery continues ahead of waiting messages while preserving their order and attachments; stop and busy admission still apply (`engine::install_gate::tests::t515a_update_admission_snapshots_keep_accepted_queue_and_attachments`, `t515a_interrupted_admission_snapshots_keep_accepted_queue_and_attachments`).

A rejected closing box keeps the sent follow-up file until the conclusion saves successfully. A repeated task becomes a new unsent offer (`engine::plan::tests::t515a_rejected_conclusion_keeps_the_sent_follow_up_file`, `t515i_conclusion_recreates_the_current_sent_follow_up`).

`save_file` replaces the destination only after the copy succeeds, preserving the old file on failure (`table::revoke_tests::t515a_failed_workspace_copy_preserves_existing_destination`).

Conversation saves are collected and published after the core lock is released (R538). Durable save paths stay synchronous; generations, retries and deletion tracking protect newer changes. Checks are in `engine/src/engine/save.rs`, `engine/tests/transcript_save.rs` and `engine/tests/failed_writes.rs`.

The data folder is `%APPDATA%\Faber` or `FABER_DATA_DIR`. Windows validates its directory chain at startup; JSON files use temporary files and rename (`workspace::DataDirectory`, `engine/tests/engine.rs`).

## Portable catalog plugins

A plugin groups only parts the existing store can check: skills, slash-command prompts, subagent definitions and
R253-portable pinned npm servers. One parent catalog id owns the source commit, whole-folder digest, part digests,
server package pins, ledger, lock, On/Off, journal and Undo; there is no second installation path. The installer never
runs shipped scripts. Hooks, binaries, postinstall, dependencies, unsupported native parts and source-wide unsafe files
reject the whole candidate. No plugin currently ships; [the twenty-candidate audit](history/research/2026-10-21/catalog-list.md)
keeps original-source pin records separate from approval and explains each rejection.

Claude Projects uses the existing checked private session plugin for skills, commands and agents. A CLI without its
plugin flag keeps the skill instruction fallback; cards and details name unavailable commands and agents. Codex keeps
its skill delivery and receives checked agent-role TOML files through per-session configuration; plugin command
prompts are unavailable, explicitly named on the card and in the detail. No personal CLI command/agent folder or
configuration is written. Chat receives only selected catalog skill text, including plugin skills, and no commands
or subagents from plugins. Servers use the existing Full access gate, project preferences and namespaced identities.
The same session-kit selector sees plugin skills and servers; there is no additional chooser.

Implementation: `engine-projects/src/tools/plugins.rs`, `engine-projects/src/tools/plugin_delivery.rs`, `ui/Catalog.tsx`,
`ui/McpServers.tsx`; checks: `engine/tests/plugins.rs` and `tests/ui/plugins.check.ts` (local fake source, parts,
whole-plugin Install, Off, Remove and Undo, delivery limits and server project choices). New UI words are hand-written
in all five locales. No extra background process, timer or permanent DOM; plugin metadata and native instruction
files fit the existing bounded snapshot. Native screen and full-app memory/processor proofs belong to the lead.

## Known incoherences

Found by the 2026-10-16 audit and not fixed yet. Touching one of these parts means fixing it or leaving it as it is,
never copying it. "Owner" marks a choice of taste or direction that needs the owner first; every item left waits for
one. Delete a line in the commit that fixes it. The weekly coherence pass (`testkit/coherence/weekly.md`) proposes new
lines and the removal of fixed ones.

- Page in Faber’s browser: the Electron pane enforces Blocked sites only for direct opens through the Rust host. Page-initiated links, history and redirects do not ask the host before loading; wiring per-hop enforcement belongs to the Electron move. Tauri checks every hop its navigation callback reports; redirects the platform does not report cannot be checked here.

## Worked example: adding a setting

Say people want to turn off the cache-warm note.

1. Check the map first: no setting covers it, and it is a preference for every conversation, so it is a field of
   `Settings`, not of a conversation, a project or browser storage.
2. Add `cache_note: Option<bool>` to `Settings` in `engine-core/src/model.rs`. The merge in `Core::save_settings` and
   `engine/tests/product_map.rs` stop compiling until the field is in both.
3. Give it one default in one place and read it there.
4. Mirror it in `Settings` in `ui/api.ts`.
5. Place its control with [product-rules.md](product-rules.md): a `Toggle` from `ui/controls.tsx` in the Settings section
   it belongs to (General), one short line, never on the conversation screen.
6. Write its label and hint in all five `ui/locales/` files by hand.
7. Extend `tests/ui/settings.check.ts` (and `testkit/src/screen/settings.rs` when it changes the real app).
8. Add its row to "Every setting" above, in the same commit.

What not to do: a second control for something that already has one, like a model select under every answer next to the
composer's model picker (R168 removed it). That is the mistake this page exists to prevent.

Unfinished agent calls loaded without a live CLI, or copied into a new conversation, retain an optional `ToolUse.interrupted` marker. The existing Subagent step and background-work projection show them stopped and exclude them from the live-helper count, even under a completed reply; known results, briefs and history are preserved without replay or an invented end time (`engine/src/engine.rs`, `settling_a_reply_interrupts_unfinished_agents_without_inventing_results`; `tests/ui/agents.check.ts`, restarted agents).
