# Product map

What Faber has today, for whoever builds the next part. [product-rules.md](product-rules.md) says where a new thing goes;
this page says what is already there, so a new part extends it instead of adding a second way to do the same thing. How
each part looks and moves is in [design/](design/README.md); where Faber is going is in [product/](product/README.md).

The map names files and keys, never line numbers. `engine/tests/product_map.rs` fails when a setting, a `ui/*.tsx` file,
a shell command or a browser storage key is missing from it; words, flows and features stay true because the commit
that changes them updates this page too. Last full audit: 2026-10-16.

| Chat | The area for conversations with one AI at a time. A chat works in a private folder of its own, or in a folder picked before its first message. | `ui/Welcome.tsx`, `ui/Thread.tsx`, `ui/Composer.tsx` |
| Projects | The area for git folders. Inside a project the person talks to an AI agent that works in the folder, or in a separate copy of it (below), with the same permission modes as Chat (R160). The old mission machinery is gone from the engine (R215): a project is worked in by talking to its agent. | `ui/App.tsx`, `ui/Projects.tsx`, `engine/src/project/` |
| Separate copy | A project conversation's own git worktree on its own branch, `faber/<a few words>-<4 characters of its id>`, made from the head the person has checked out when its first message is sent, in a git repository with a commit and while the project keeps separate copies (on by default, Settings > Projects; R201). The first message shows at once with its answer typing, and the copy is made behind it (a second or two on Windows); the agent starts when the copy is there, and a copy that cannot be made ends that answer with `error.copy.failed` (the message goes back in the box) while the next message in the conversation tries the copy again, never the folder (the copy is named on the conversation and saved before git starts, so a restart in between still ends in the copy). Its agent works only there, so two conversations and the person's checkout never touch the same files; the agent brings the work back itself (commit, push, pull request), and Faber never merges. A branched conversation gets its own, from the source's branch. A conversation the agent starts gets its own, named after its title, and its brief waits for it. It goes with its conversation, or at start once its work is in the person's branch (or its upstream) and nothing is left uncommitted; work found nowhere else is never deleted without the person saying so. A conversation that began in the folder stays there | `engine/src/project/copy.rs`, `engine/src/engine/copies.rs`, folders in `copies/<conversation id>/` |

| Branch | Editing a past message starts a new conversation from that point. | `ui/Thread.tsx` |
| Queue, steer | A message sent while an answer runs goes into the running turn, Codex and Claude Code alike, and joins the conversation when the CLI takes it in; one for another vendor, or behind one still waiting, waits in a queue, and its "Send now" hands it to the running turn of the same vendor, or else puts it first. A waiting queued chip offers Edit beside Remove and Send now: a small box in place, Save and Cancel, Enter to save, Shift+Enter for a new line and Escape to cancel. Only its text changes, with the same id, order and attachments, saved with the conversation. Empty text or a message already handed to the CLI, sent now or removed is refused; a save refused because the message left returns the edit to the conversation's message box, appends after a blank line to an existing draft, closes the editor, focuses the box and explains it once in a calm line. Removed rows leave no editor registry: saved edits recover from the unsent store even after Settings or restart. Escape cancels from every editor control, except during composition. Writing never stops anything: a line written while subagents work in the background becomes a turn of its own and they go on (a live Claude Code capture). | `engine/src/engine.rs`, `engine/src/claude.rs` |
| Keep going | A project conversation that goes on by itself while the person is away (R199): each end of a turn sends the next one, until the whole request is done and checked (the first "nothing is left" makes Faber ask the agent once to reread the original request; a second one ends it, even in a turn the person sent in between (R241); the stop line never shows, while it arrives or after, with Keep going on or off), the agent asks something nobody answered, six turns in a row fail (it rests one, five, then fifteen minutes between), 200 turns that did real work went out (a quick turn with no tool rests two to five minutes and does not count), or no AI it may go to is a known subscription (nothing billed per use is spent unattended). Waiting on CI, a queue or a build is never a reason to stop. A question the agent asked that nobody answers in ten minutes gets its first choice, told on the reply (`autoAnswers`, with the other choices); permission cards are never answered. It survives a restart of Faber: it goes on after a short wait for the accounts to be read (a rest it was in is kept). Its row in the running column shows how far it has come (turns of work, how long it has run, the last line the agent wrote) and the wait it is in (a rest, a retry, an update); after half an hour on its own, the newest reply starts with one quiet line, "While you were away", with the turns of work, the moves to another AI and the questions Faber answered (`away`), under it "Pages it left open": the latest step on each page Faber's browser opened during those turns, the newest four, a small picture each (none where none was kept) with that step's words (`awaySites` in `ui/Site.tsx`), and each question it answered is told on the reply (`autoAnswers`). Before each turn it sends, Faber compacts the agent's context by itself at the moments a careful person would (R260): after a reply that closed a task once the context holds a quarter of its window (never under 80K tokens), and at any turn from three fifths; once per turn, never before the check turn, only on a session it may spend on unattended, with no setting. The running list shows it at work meanwhile, and the turn follows the summary. A message Faber sends by itself carries why (`wake`) and takes no row (Faber's own message). | `engine/src/engine/keep_going.rs`, `engine/src/engine/by_itself.rs`, `ui/Composer.tsx`, `ui/keep-going.ts`, `ui/KeepGoingNote.tsx`, `ui/Running.tsx`, `ui/Thread.tsx` |

| Agent's plan and closing box | A project's own agent calls Faber's progress tools (R248; Claude Code sees them as `mcp__faber__plan`, `mcp__faber__status` and `mcp__faber__wrap_up` from the same MCP server as the helper, Codex as the dynamic tools `plan`, `status`, `wrap_up`). ## Settings screen

Five sections, in this order, all at one width (720 px). Nothing else is a Settings section. Every section speaks one grammar: a
group is a card, an option is one row (its name and one short line at the left, its control at the right), and a longer
text unfolds under the row from a small "?" beside the name (keyboard reachable, closed by default, not in the page while
closed). There is no "Learn more" link. The version ("Faber 1.2.3") closes the list of sections, once.

- **General**, in groups. *You*: Language (follow the system, or one of five), Your name, "Do you already use AI?" (the first run's
  answer), "Watch again" for the tutorial (opens a fresh chat and plays it again), Keyboard shortcuts ("Show" opens the list). *How the AI works*: Permissions
  for Chat and Projects (a menu of five modes, each with its one line; "Full access" by default), Web search, Your CLI
  hooks (only acts in the guarded modes; in "Full access" it shows on and locked, with "In Full access your own hooks always run."), Chat working folder (with Recents; acts on the open chat
  while it has no message; the row exists only when Settings was opened from Chat, where its control does), and a folded
  "Codex" group (reasoning summary, answer length; Codex only, closed by default). *Notifications and system*: Notify me,
  Play a sound, and on Windows keep the computer awake while Faber works and start with Windows. *Updates*: Receive
  previews (off by default, R156).
- **Projects**: first *Skills for projects*, one card closed like a project's that says how many are on ("2 of 21 on") and
  opens to one switch per skill of Faber's catalog (its name, one line and its licence; the "?" names its repository); on
  downloads it from that repository at the pinned commit and checks its files, off removes it, for every project's agent
  (step 1 of the catalog, R247). Next, *Tools for projects*, the same card for the catalog's tool servers (step 3), which reach a
  project's agent in Full access only (they run outside the CLI's sandbox, as Faber's own browser): each one an npm
  package Node.js runs (the card's line names Node.js 20.19 or newer; on without Node says so), downloaded
  from npm at the pinned version and checked the same way, its data collection and update checks turned off by Faber's own
  flags. The first is the measurement server (traces, memory, Lighthouse, in a Chrome with no window). Then per project, closed until opened, in the same cards and rows: checks (confirm, edit, view) and "A separate copy for each
  conversation" (switch, on; it acts on new conversations only). Applies to that project only.

  swatches, any colour, hex). *Text and layout*: background, text font, heading font, text size, spacing, corners,

the other subscription or waiting (the quota card, just in time, per message); permission answers (the cards).

## Every setting

`settings.json` in the data folder holds the struct `Settings` of `engine/src/model.rs`; `ui/api.ts` mirrors it by hand.
The only writer is the `save_settings` command; the merge in `Core::save_settings` (`engine/src/engine.rs`) builds a full
`Settings`, so a new field does not compile until it is merged. A patch sets a value and never clears one (an empty
`userName` is the only way back to none). There is no "settings changed" event: Rust readers read the file when they need
it, and the screen takes the saved settings from the answer of `save_settings`.
A switch's default lives once, in `impl Settings` (`engine/src/model.rs`): Rust readers call its method, and the shell
sends the screen every switch already filled in (`Settings::shown`), so the screen keeps no default of its own. The
effort a model starts at is the one exception the screen shows before the engine sees it: `DEFAULT_EFFORT` in
`ui/api.ts`, kept equal to `Effort::default()` by a test in `engine/src/router.rs`.

"Lives on" is one of a closed list: a Settings section, the first run, the composer, a just-in-time card, or none. A
choice a person makes anywhere else (a work screen, a banner) is an incoherence.

## Worked example: adding a setting

Say people want to turn off the cache-warm note.

1. Check the map first: no setting covers it, and it is a preference for every conversation, so it is a field of
   `Settings`, not of a conversation, a project or browser storage.
2. Add `cache_note: Option<bool>` to `Settings` in `engine/src/model.rs`. The merge in `Core::save_settings` and
   `engine/tests/product_map.rs` stop compiling until the field is in both.
3. Give it one default in one place and read it there.
4. Mirror it in `Settings` in `ui/api.ts`.
5. Place its control with [product-rules.md](product-rules.md): a `Toggle` from `ui/controls.tsx` in the Settings section
   it belongs to (General), one short line, never on the conversation screen.
6. Write its label and hint in all five `ui/locales/` files by hand.
7. Extend `tests/ui/settings.check.ts` (and `testkit/src/screen/settings.rs` when it changes the real app).
8. Add its row to "Every setting" above, in the same commit.

What not to do: a second control for something that already has one, like a model select under every answer next to the
composer's model picker (R168 removed it). That is the mistake this page exists to prevent.
