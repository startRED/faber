# B8: Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Settings becomes five sections (General, Appearance, Connected accounts, Usage limits, Privacy). Appearance is a draft with a live preview and the measured contrast, applied only by "Use this look" once the save worked; Connected accounts opens the account cards of B7 in `manage` mode and comes back with the draft intact; Usage limits shows the quota readings that left the header; Privacy states what stays on this PC.

**Architecture:** The rules the screen needs (what the draft is compared with, what the controls show before the shell has answered, the three contrast readings, a typed colour, the lines of the usage section) are plain functions in `ui/draft.ts` and `ui/sidebar.ts` that know nothing about the screen. The draft lives in `ui/Settings.tsx`, so it survives a visit to the account cards; `ui/Appearance.tsx` is the section that edits it, and it sends every change through the existing `previewer` (`ui/appearance.ts`), which now also hands back the draft an answer belongs to. The page wears a look only through `saveSettings` in `ui/App.tsx`, as it did for B3. The engine and the shell are not touched: B3 already has `preview_look`, the error-carrying `save_settings`, `save_theme` and `open_theme`.

**Tech Stack:** SolidJS + TypeScript (built by Vite), Rust 2024 for the screen scenarios of the test runner (`cargo t`, suites `rust`, `ui` and `screen`; the `screen` suite drives the real hidden window over WebView2's DevTools port).

**Spec:** `docs/superpowers/specs/2026-10-11-faber-redesign-design.md`: B8 (all of it), B0 (commit 10, "B8: Settings"), B3's data flow (steps 3 to 5: previews, ordering, the save), A13 (the design system: what a person may customise and the three locked meaning colours), A10 and AI-21, and the Review-log lines about Settings, appearance, usage limits, accounts and theme files. Erick's decisions (`E:\Documentos\ProjetosIA\faber-notas\decisoes.md`): R77 (the three meaning colours are locked and shown read-only) and the decisions that give the themes. The visual design is `E:\Documentos\ProjetosIA\faber-notas\design-final\` (mock s5 and its notes). This is commit 10 of the order in B0. It replaces B3's simple Appearance section and uses B7's `manage` mode of `Setup`.

## Global Constraints

- Code, comments, docs and commit messages are in English. Original code only; nothing from TL-ADE, TL-Control or TL-Orchestrator.
- Never read, copy, store or forward CLI credentials or session tokens. This plan touches none; Connected accounts only opens B7's cards, which start each CLI's own sign-in.
- Child processes never go through a shell. This plan starts none.
- Do not use vendor names in product, feature or package names. "Claude" and "ChatGPT" appear only as the names of the accounts and usage lines, as today.
- Every text on screen lives in `ui/locales/`. Each language is written by hand, never machine-translated; English (`en.ts`) is the source. The engine returns keys, never sentences.
- Memory: Faber with no CLI running stays under 500 MB when complete, and the end-to-end test fails above 250 MB today. The preview and the six look cards are small spans drawn with the shell's own tokens: no canvas, no extra process and no timer (the scenario `after the six looks were applied in turn` keeps measuring).
- Telemetry stays off; the Privacy section says so and adds no setting for it.
- The screen never computes a colour: the shell does (`preview_look`, `save_settings`). `ui/draft.ts` only reads the contrast pairs the look carries.
- Spec values, verbatim: the six preset cards in the order Sala, Oficina, Bancada, Manhã, Alto contraste, Cobalto; five accent swatches plus a custom colour (native colour input and a hex field); the ground (5 options), the text font (3), the heading font (4), the size slider (13 to 18 in steps of 0.5), density (2), corners (3), motion (3); the preview panel "Not applied yet" with a scaled-down live chat, the measured contrast of text, faint text and accent, and the three effect switches; "Back to default" resets the draft to Sala, the theme's sizes and the system's motion; "Use this look" saves first and applies only after the save succeeded; Privacy says "Telemetry: off.", "History: only on this PC." and "Your Claude and Codex logins: Faber never reads them."; the switch "Projects run my own CLI hooks" lives in General.

## Review Focus

Failure modes the spec implies and a person would meet, most likely first. Each one has a test in the task named after it.

1. **The disk refuses the save behind "Use this look"** (full disk, a read-only folder, an antivirus holding the file). Expected: the page keeps its look, the draft stays so the same click can be tried again, the error key's sentence shows as an alert, a switch in General goes back to where it was, and once the disk works the same draft saves and the alert goes away. Pinned by: Task 4: `a settings save that fails changes nothing, says why, and works again once the disk does`.
2. **An accent next to a meaning colour, or text that is not a colour** (#f0a030 beside amber; "banana" in the hex field; the short `36C`). Expected: a sentence in the action bar, the field and the draft go back to the last accepted ones, "Use this look" stays as it was, and a short or upper-case hex is read, not refused. Pinned by: Task 3: `settings: a typed colour is read as #rrggbb in lower case or refused`. Task 4: `an accent too close to a meaning colour is refused in words, and the draft goes back`.
3. **Leaving for the account cards, or closing Settings, with a look that is not used yet.** Expected: opening and closing the cards brings Settings back on the same section with the same draft and the page unchanged, and keyboard focus is on "Manage accounts" again; Esc or Back from Settings drops the draft. Pinned by: Task 4: `the account cards open from Settings, and Close brings Settings back with the look not yet used`.
4. **High contrast as the look on the page.** It keeps its own ground, which it reports as its own id and which is not one of the five a person can pick, so naming the ground by `look.ground.<id>` would crash the section on open. Expected: Appearance opens in every look and names that ground by the look. Pinned by: Task 3: `settings: every look names the ground it reports, even High contrast, which keeps its own`. Task 4: the existing `every look fits the new conversation...` opens Appearance in each of the six looks.
5. **A vendor that has not reported, one with only an old reading, one with one window, and a reload.** Expected: one line with "—" for no reading, the window's name with "—" for an old one, the short window first, and the same figures after the page loads again. Pinned by: Task 3: `settings: usage lines are the short window first; an old reading keeps its name and loses its numbers; none gives one empty line`. Task 4: `the quota in the sidebar opens Settings on the usage limits, and a reload shows the same figures`.
6. **A quick run of changes** (dragging the size slider, clicking several looks) answered out of order. Expected: the preview and the controls end on the newest draft, never an older one. Pinned by: Task 3: `settings: the previewer hands the draft back with its answer, and only for the newest request`, next to B3's `two previews answered in reverse order leave the screen on the later request`.
7. **A narrow window or a large text size** puts the preview beside controls that no longer fit. Expected: below 1100 px the preview stacks under the controls and nothing sticks out sideways. Pinned by: Task 4: `every section of Settings says its part` at 900 px wide.

import themes from '../src-tauri/src/themes.json';
import type { Appearance, Look } from './api.ts';

// The pure rules behind the Appearance section of Settings (ui/Appearance.tsx): the draft the person is working on, what
// it is compared with, and what the preview panel reads off a look. The screen never computes a colour: the shell does,
// and these functions only read its answers.

/** The factory look: Dark Room, the theme's own sizes and the system's motion. */
export const factory = (): Appearance => ({ base: themes.default });

// Keys in a fixed order, so two appearances that make the same choices read the same.
const canon = (value: unknown): unknown => {
  if (Array.isArray(value)) return value.map(canon);
  if (value === null || typeof value !== 'object') return value;
  return Object.fromEntries(
    Object.entries(value)
      .filter(([, v]) => v !== undefined)
      .sort(([a], [b]) => (a < b ? -1 : 1))
      .map(([k, v]) => [k, canon(v)]),
  );
};

/** Whether two appearances make the same choices. No appearance at all is the factory look. */
export function sameChoices(a: Appearance | undefined, b: Appearance | undefined): boolean {
  return JSON.stringify(canon(a ?? factory())) === JSON.stringify(canon(b ?? factory()));
}

/** What the controls show: the draft's own choices over the last answer's, which has every choice filled in from the
 * base. Between a change and its answer a control already shows the choice, and the fields the draft leaves out show
 * what the look gives them. */
export function shown(draft: Appearance, look: Look): Look['appearance'] {
  const own = Object.fromEntries(Object.entries(draft).filter(([, v]) => v !== undefined));
  return { ...look.appearance, ...own };
}

/** One of the three contrast readings of the preview panel: text, faint text and the accent, each on the background. */
export interface Reading {
  id: 'text' | 'faint' | 'accent';
  ratio: number;
  pass: boolean;
}

const READINGS = [
  ['text', 'ink'],
  ['faint', 'ink-3'],
  ['accent', 'accent'],
] as const;

/** The readings the look carries, in the order the panel shows them. */
export function readings(look: Look): Reading[] {
  return READINGS.flatMap(([id, ink]) => {
    const found = look.checks.find((c) => c.a === ink && c.b === 'bg');
    return found ? [{ id, ratio: found.ratio, pass: found.pass }] : [];
  });
}

/** The pairs of colours that are too close to read, as the look names them ("ink-3 / s3, ..."); empty when every pair
 * passes. A look with a failing pair cannot be applied. */
export const failingPairs = (look: Look): string =>
  look.checks
    .filter((c) => !c.pass)
    .map((c) => `${c.a} / ${c.b}`)
    .join(', ');

/** A colour typed by hand: `#rrggbb`, `rrggbb` or the short `#rgb`, in any case. The answer is `#rrggbb` in lower case,
 * or undefined when the text is not a colour. */
export function normalizeHex(text: string): string | undefined {
  const hex = /^#?([0-9a-f]{3}|[0-9a-f]{6})$/i.exec(text.trim())?.[1]?.toLowerCase();
  if (!hex) return undefined;
  return `#${hex.length === 3 ? [...hex].map((c) => c + c).join('') : hex}`;
}

type Tokens = Record<string, string>;
const css = themes.css as unknown as { base: Tokens; themes: Record<string, Tokens>; presets: Record<string, Tokens> };

/** The key of the words that name a ground. A look that keeps its own ground (High contrast) reports it as its own id, which
 * is not one of the five a person can pick; it is named by the look. */
export const groundKey = (id: string): string => (themes['user-controls'].grounds.includes(id) ? `look.ground.${id}` : `look.${id}.name`);

/** The background a ground gives, for its chip: the same colour its theme or preset uses. */
export const groundColor = (id: string): string => css.themes[id]?.bg ?? css.presets[id]?.bg ?? css.base.bg!;

import { For, Show } from 'solid-js';

// The two controls Settings is made of: a group of buttons of which one is on, and a switch.

export type Option<T> = [T, string];

/** Choices that exclude each other. The one that is on says so with `aria-pressed`. */
export function Segmented<T extends string | number>(props: { id: string; label: string; value: T | undefined; options: Option<T>[]; onPick: (v: T) => void }) {
  return (
    <div class="ctl">
      <span class="lbl" id={props.id}>
        {props.label}
      </span>
      <div class="seg-ctl" role="group" aria-labelledby={props.id}>
        <For each={props.options}>
          {([v, text]) => (
            <button type="button" aria-pressed={v === props.value} onClick={() => props.onPick(v)}>
              {text}
            </button>
          )}
        </For>
      </div>
    </div>
  );
}

## Deviations from spec

1. **The preview says "Applied" when it is.** The spec labels the panel "Not applied yet". Here the label reads "Not applied yet" while the draft differs from the saved look and "Applied" when it does not, and "Use this look" is disabled when there is nothing to apply, while a save runs, and while a colour pair fails. A label that says "not applied" next to the look that is on the page would be wrong.
2. **The actions sit in a bar that stays in view, not inside the preview panel.** The spec lists "Actions" after the panel without a place. The controls are taller than an 800 px window, so "Back to default" and "Use this look" are in a bar at the bottom of the section that does not scroll away; the sentence of a refusal shows in the same bar, next to the button it explains.
3. **A failing contrast pair is shown before the save.** The shell reports failing pairs in `look.checks` and refuses them on save (`error.look.pairFailed`). The screen reads the same pairs, shows that sentence in the bar and keeps "Use this look" disabled, instead of letting the person click and fail.
4. **A refused accent puts the draft back.** The spec says "Use this look stays as it was". The hex field and the draft also go back to the last look the shell accepted, so the controls never show a colour the preview does not wear. A hex typed in the short form (`36C`) or in upper case is read and normalised, and text that is not a colour gets its own sentence (`set.hexInvalid`).
5. **The quota in the sidebar opens Usage limits.** B5's text says the footer "opens Settings > Usage limits"; nothing could do that until the section existed. Ctrl comma and the Settings button still open General.
6. **Esc and Back.** Esc in the account cards that Settings opened closes them and brings Settings back (not the shell); Esc or Back in Settings closes it and drops a draft that was not used. The spec says Settings closes with Esc "as today" and does not cover the cards' Esc.
7. **Settings still replaces the whole shell.** In the mock the sidebar stays beside Settings. This plan keeps today's behaviour (the sidebar is hidden while Settings is open), because a sidebar that stays would need its own focus and narrow-window rules, and B8's list of files does not include the layout.
8. **"Open file" fills the draft.** The spec says "Save as file" and "Open file" (B3). Opening a file puts its look in the draft and says "Opened “name”. Look at the preview, then use it." It never applies a file at once. "Save as file" saves the draft, not what is on the page.
9. **Two font names are shortened.** The text font buttons read "Archivo", "Plex Sans" and "Atkinson" (they were "IBM Plex Sans" and "Atkinson Hyperlegible"), because a group of three buttons beside the heading fonts has no room for the long names. The families are the same.
10. **The words of the hooks switch.** It reads "Projects run my own CLI hooks" (the spec's text) with the old sentence's explanation kept as its hint. The section's name in the list is "Connected accounts" (the spec's name) instead of "Subscriptions"; `empty.noAiBody` and the B7 scenarios that looked for that word follow it (they ask for the section's key).
11. **More files than the spec lists.** The spec names `ui/Settings.tsx`, `ui/api.ts`, `ui/locales/*.ts` and `testkit/src/screen/app.rs`. `ui/api.ts` is not touched, because B3 already has every command this needs.
