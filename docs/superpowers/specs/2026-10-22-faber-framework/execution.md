# Execution and quality

Status: Extension proposal. The approved R435 method takes precedence.

Revision 2: [adaptive work](intelligence.md) selects the execution path, and [domains.md](domains.md) defines
non-code acceptance. The risk-sized loop here controls authority and completion regardless of that selection.

## The current execution unit

Use normal project conversations, their separate copies, helpers, started conversations, saved plans and engine
checks. Do not bring back mission roles, journals, envelopes, coordinator, isolated mission proofs or local-build
machinery removed in R215. Existing self-development and landing remain the current workflow.

The lead keeps the user's thread. Helpers make scoped contributions. Faber records checks and authority.
A fresh independent reviewer handles the required review. These responsibilities do not require always-running
agents, departments or fixed assignments of models to roles.

## Risk-sized work, preserving R435

| Path | Preparation | Completion |
| :--- | :--- | :--- |
| Question | Relevant sources and context | Honest answer; no project scaffolding |
| Small | Bounded reversible task | Applicable checks, close; no forced memory entry |
| Normal | Contract in existing plan: Extends/New, proving check, measurable target where needed | Build, engine checks, receipt and scoped close |
| Risky | Normal plus boundary analysis and independent review | Review gate; security has two independent reviews |

Set size at plan time. The approved permission-layer escalation raises risk before an unclassified or sensitive
call runs and holds it until its contract exists. Do not implement a second classifier in framework prompts.
Do not lower validation, accessibility, error handling or review to reduce token use.
A planning-only request ends with a reviewed plan, not an automatic implementation.

## Outcomes before detailed tasks

Capture the original requirement and what should be true when finished. Identify non-goals, existing product
surfaces, applicable criteria and dependencies. Preserve the person's wording and authorship through source refs.
Visible changes use the current product map, product rules, design page and relevant taste cards.
Contradicting an owner decision requires the person's decision, never a technical plan edit.

Detail the immediate next deliverable. Keep later milestones at outcome level until dependencies stabilize.
Technical uncertainty gets a bounded investigation and an exit criterion, not a made-up delivery date.
Use adopted task lists and link selected follow-ups to their active plan; remove them only under their existing
completion rules. A roadmap reference does not authorize starting an idea or change standing-goal stop conditions.

## Coordination and economy

Run ready work whose dependencies are satisfied, respecting owner priority, current project limits, grants,
subscription quota and measured resource headroom. Reuse the existing conversation/helper admission limits.
Start with one writer; parallelize only independent scopes where the saved work exceeds duplicated context,
briefing and integration cost. A reviewer needs independent context, not the writer's explanation of why it is right.

Use Auto and existing kits. Do not add another model picker or assume that cheaper models pass the quality floor.
Count lead, helpers, review, retries and cache effects. Preserve the current 150%-of-estimate economy behavior;
an estimate overrun is not a spend authorization or a reason to discard unfinished output.
Hard resource and authorized spend limits still control admission. Unknown usage remains unknown.

Keep dependent work serial. While a check or review runs, continue only independent authorized work. A worker
claim is not itself a validated process lease or an integration check. Future stronger write-ownership guarantees
must be implemented against the current copy/process architecture, not borrowed from the removed mission engine.

## Truthful lifecycle

The UI may describe proposed, ready, working, checking, accepted and delivered outcomes. These are projections of
plan revisions and existing execution/evidence records, not a new editable state machine stored in Markdown.
Awaiting a decision, dependency, quota, cancellation and unavailable evidence remain explicit conditions.
A resource wait does not automatically mean the person must answer a question.

A plan's done checkbox is self-reported. Promote an outcome to verified only when all applicable required evidence
matches its current requirement revision and candidate, and required independent reviews are recorded.
Use pass/fail/not-run; non-applicability needs an explicit reason and cannot disguise an omitted check.
Unrelated failures remain visible and do not turn into passes. A declared exception requires project authority.

Reuse the verifier's recorded results and content keys. Add the missing outcome linkage and independent-review
receipt through R435's gate before claiming exact-outcome verification. Any change to relevant inputs makes
applicable checks/reviews stale. Check combined work after integration; separate passing parts do not prove the whole.
Accepted locally, incorporated into the destination and published/installed are separate facts.

## Independent review

Follow R435 and product-rules: fresh read-only session, another vendor when quota allows, same-vendor fallback
when appropriate. If no required reviewer can start, close as not reviewed rather than done. Security requires two
separate records. The writer never approves their own work.
Blocking findings need a reproducible failure or concrete evidence. Accepted resolutions are retained so settled
findings do not loop indefinitely. Optional style improvements do not hold a valid delivery hostage.

## Repair and recovery

Reuse the existing verifier's up-to-two automatic repair turns; do not stack another two-attempt loop on top.
Classify failure first: implementation, missing context, environment, unstable check or wrong requirement.
A retry needs a changed hypothesis or concrete correction. After its bounded attempts, keep evidence and output,
say unfinished, and continue only independent authorized work. Escalate a specific issue, not every routine step.

Resume from saved plan/goals, check journal, latest output and changed source revisions. Current saved plans have
no independent version history; adding revision-aware recovery is part of this proposal, not a current guarantee.
Cancellation stops new admissions and settles active processes safely. Permission revocation applies before the
next effect. An ambiguous network write or external action is reconciled, never blindly repeated after a crash.

## Complete-product verification

| Kind | Concrete evidence | Person's role |
| :--- | :--- | :--- |
| Software and mods | Reproducer, relevant checks, real-user path, rendering and resource measures | Product direction |
| Research | Primary sources, dates, claim/source mapping and uncertainty | Trade-off decisions |
| Images and design | Dimensions, inspected output, brief coverage and provenance | Taste and identity |
| Documents and spreadsheets | Rendered pages, consistency, formulas and recalculation | Content/business judgment |
| Video/audio/3D | Export, duration, timing, clipping and sampled inspection | Creative judgment |
| Automation | Preview where feasible, effect receipt and recovery route | Reserved external authority |

Use only available tools, installed capabilities or the catalog. Unsupported checks remain not run.
Preserve browser handoff for logins/captchas/payments. Sending, publishing, paying and destructive actions require
the appropriate authority; task completion does not grant it. Recipes may be part of a requested deliverable,
not a new framework-written `.faber/recipes` library forbidden by the approved file model.
