# GSD: current lineages, complaints and counterevidence

Status: Research for Flow revision 2, consulted on 2026-10-22. No competitor was executed or locally reproduced.

## Lineages and freshness

The archived [original repository](https://github.com/gsd-build/get-shit-done) directs its line to
[GSD Core](https://github.com/open-gsd/gsd-core). The archived [GSD 2 repository](https://github.com/gsd-build/gsd-2)
directs its line to [GSD Pi](https://github.com/open-gsd/gsd-pi). Core and Pi are separate comparison targets.
Version numbers across those repositories are not a single increasing sequence.

The current Pi README inspected here advertises v1.22.0, lightweight-model updates and receipt-aware closeout.
Earlier search snapshots showed older versions. Similarly, Core #4078 appeared open in a search result, but its
refreshed page showed closed via #4301. Use page bodies, pin a tag/commit and timestamp, and distinguish stable
releases from development branches. Do not portray archived bugs as uncorrected bugs in current Pi.

Method: directed public docs, releases, issues/discussions and targeted searches by failure category, followed by
fresh page-body checks for current Pi cases. The GitHub API was unreachable on this PC. This is not a census,
frequency estimate or execution-based verification. AI-generated triage is not independent reproduction.

## What current GSD already does

[Pi auto mode](https://github.com/open-gsd/gsd-pi/blob/main/docs/user-docs/auto-mode.md) documents authoritative
database state, derived Markdown, focused fresh sessions, progressive plans and milestone reconciliation.
Therefore durable runtime state and readable projections are parity requirements, not Flow inventions.

[Pi cost management](https://github.com/open-gsd/gsd-pi/blob/main/docs/user-docs/cost-management.md) documents per-unit
usage and budgets. [Its visualizer](https://github.com/open-gsd/gsd-pi/blob/main/docs/user-docs/visualizer.md) already
shows progress, dependencies, history and metrics. A visual roadmap alone does not make Flow superior.

[Token optimization](https://github.com/open-gsd/gsd-pi/blob/main/docs/user-docs/token-optimization.md) documents
profiles, compression and complexity routing. Its budget table describes dropping decisions/requirements from
minimal dispatch context. That is a documented trade-off to test, not proof that every run loses requirements.
Flow instead keeps mandatory task requirements intact and saves on irrelevant context and optional stages.
The page's advertised savings are the project's claim, not an independently confirmed result used here.

[Current troubleshooting](https://github.com/open-gsd/gsd-pi/blob/main/docs/user-docs/troubleshooting.md) already
describes persisted liveness wedges, controlled recovery and refusal to regenerate missing user-authored content
from incomplete database rows. Do not present loop detection or safe recovery as missing from all current Pi.

## Implications

Flow must meet the existing strengths above before a superiority comparison is meaningful. The proposed additional
bar is useful cross-domain results, calibrated task/model/verification selection, original requirement fidelity,
complete resource accounting and a beginner-readable experience native to Faber. Each needs measurable evidence.
Compare Core and Pi separately on overlapping tasks; do not score a non-code task as their failure merely because
their stated product is a coding agent. Benchmark any claimed generalized configuration explicitly.
