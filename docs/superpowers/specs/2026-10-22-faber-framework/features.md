## Acceptance and removal conditions

| ID | Minimum observable acceptance | Cost / simplification condition |
| :--- | :--- | :--- |
| FF01 | Wrong root, changed source and stale checker cannot yield a current pass | Bound fingerprint scope; no repeated whole-repository scan |
| FF02 | Required passages and negative constraints survive delegation/resume; missing inputs explicit | Lazy relevant content; do not add five duplicate planning files |
| FF03 | Candidate change invalidates applicable evidence; historical result remains readable | Small native fields/projections; no separate database or running service |
| FF04 | Qualified light/mixed/frontier strata improve or preserve declared quality floors with full costs | Remove scaffolding that adds overhead without value; preserve stable session/cache behavior |
| FF05 | Separable work benefits without degrading sequential cases; unauthorized compositions refused | Cap work by task resources, not number of personas; no arbitrary executable workflow persistence |
| FF06 | Interruptions and ambiguous external effects reconcile without duplicate actions or lost accepted results | Reuse valid outputs; no polling or replay simply to regenerate a summary |
| FF07 | Seeded defect found; safe contrast and unrelated case produce no corresponding false alarm | Track missed faults and false alarms together; do not buy silence by weakening review |
| FF08 | Appropriate artifacts are actually inspected/computed with available tools and known limitations | Load only relevant procedure; domain scores cannot hide missing hard requirements |
| FF09 | New users find now/next/blocker; reported checkboxes never appear as verified outcomes | Paged detail, keyboard/text states, existing resource limits, zero idle service |
| FF10 | Paired held-out results and costs support promotion; changing check answers cannot improve score | Bounded runs; no automatic active-policy mutation or same-data tuning/evaluation |
| FF11 | Comparable accepted tasks expose intervention time and errors after delivery, with missing data explicit | Do not count fewer questions as a win when mistakes increase; no background surveillance |
| FF12 | Real repeated task succeeds with declared tools, trigger, authority, stop condition and recovery | No automatic webhook/server or assumption the PC works while off; local/hosted boundary explicit |

FF11 measurement should include the person's optional correction/review time, required decisions, false findings,
reopened work and confirmed downstream faults. Do not monitor unrelated computer activity. A necessary question can
be the best action; reducing questions or maximizing autonomous time is never a success criterion by itself.

## Roadmap placement, not another product

- Phases 1a/3: complete approved method first; qualify FF01–07 through existing project work and toolbox.
- Phase 2/3 benchmark integration: FF10/11 baseline collection where current product supports it, without reordering phases.
- Phases 3/4: linked outcomes and general software/domain adapters, FF08/09, on the same records and native surfaces.
- Phases 6/8/9/10: deepen design/media/apps/mods checks as actual specialized tools are qualified; general work stays available.
- Phase 7: FF12 routines, separately from creating a reusable skill or running a task once.

These candidates do not change the main phase order, approve a new vendor or promise every domain is already covered.
Existing frontend-craft/frontend-proof are input capabilities for FF08, not a reason to build another design engine.
Native tool availability and its current proof must be confirmed at dispatch time while other lanes keep changing it.

## What is different from installing a framework

BMAD, GSD and the researched frameworks already contribute strong mechanisms; several offer routing, durable state
and receipts. Faber's candidate advantage is the integrated combination: exact intent and current sources, adaptive
support for both light and frontier models, real domain-specific acceptance, reliable recovery, attention-aware
evaluation and an understandable native outcome route. Their integration is still unbuilt and their advantage still
unmeasured. [Qualification](qualification.md) determines what a future comparative claim may actually say.
